# Auto Research

The current conversation Agent owns understanding, planning, delegation, iteration and stopping. Use existing tools and session history. Never call a Research API, start a supervisor/coordinator, or impose a fixed role pipeline.

1. Understand the objective, expected deliverable, available evidence/data, constraints, research type and budget. Ask via `ask_user_question` only for material missing assumptions or objective/protocol approval when needed; conversation replies are the continuation path.
2. Read [evaluation-design.md](references/evaluation-design.md). Before substantial research, save a versioned `evaluation.yaml` with success criteria, objective measures or nonnumeric review checks, data sources/splits, validity constraints, budget and stopping conditions. Do not invent a universal quality score. Configure the generic `execution_budget` tool with `research_id: "<research-id>"` before the first execution to bind a persistent shared research allowance. Reuse this ID on continuation; parent and child operations spend from the same cap. Configure it before retrieval, delegation or computation with the agreed remaining time and execution-call allowance. A tool call is not the same as an experiment: record both budgets and use bounded one-experiment commands. Runtime limits cannot be expanded in the same operation.
3. For quantitative work, build a task-specific evaluator in the research workspace (Python, R, SQL, script or existing scientific tool). Validate against known answers and edge cases; establish comparable baseline results with the same metric, data version and evaluator. For literature/exploratory work, use coverage, independent evidence, verified citations and explicit gaps; an executable evaluator is optional.
4. When independent review adds value, call `subagent` with `agent: "auto-research/reviewer"` to review the protocol before execution, at consequential milestones and before delivery. Pass protocol, evidence and file paths; repair blocking issues before continuing. A Reviewer PASS never overrides a failed objective metric, and a passing metric never overrides critical validity failures. Simple work can use explicit self-checks; explain any omitted independent review.
5. Read [experimental-research.md](references/experimental-research.md) for experimental or mixed work, [deep-research.md](references/deep-research.md) for knowledge investigation, and [evidence-management.md](references/evidence-management.md). Read [experiment-safety.md](references/experiment-safety.md) before any candidate execution. Delegate implementation hypotheses to `auto-research/experimenter` and evidence subquestions to `auto-research/researcher` when useful. Do not force all roles or a fixed pipeline. The existing `subagent` tool supports `{agent, task}`, `{tasks: [{agent, task}, ...]}` (up to four in parallel) and `{chain: [...]}`; no mandatory chain. Multiple tasks may use the same researcher role.
6. Researcher may autonomously use its exact declared Web Access MCP tools and explicitly declared scientific MCP tools, intersected with the parent's active tools. Hidden children require explicit tool preauthorization in MCP settings; `ask` fails immediately with a permission dependency, never autoapproves or waits for invisible UI. Use the parent's normal approval path for one-off retrieval, then supply evidence, or ask the user to authorize the specific tool in existing MCP settings. Never use Bash/curl to bypass MCP policy. Children cannot ask users or enlarge permissions/budgets. **Current execution mode is code generation with parent-controlled execution, not fully autonomous sandbox execution**: Experimenter returns candidate code; the parent inspects and saves it in its separate candidate directory. Do not give Experimenter write/edit/bash/notebook permissions without actual filesystem/process isolation. The parent uses existing controlled scientific execution tools only after checking safety and keeps frozen evaluator, baseline, original data and other candidates protected. Candidate self-reported scores are local observations; the parent independently reevaluates using the same trusted evaluator. Save parameters, seeds, environment, input/code/data/evaluator digests, raw outputs and real execution/artifact/provenance references.
7. Integrate structured claims, conflicts and gaps; evaluate; review; decide continue, change strategy, ask for a dependency, or stop. Stop on goal achieved with no blockers, adequate coverage with no material progress, exhausted budget, missing dependencies, or material risk. Convergence and Reviewer PASS do not prove correctness. Report budget exhaustion as incomplete.
8. Read [reporting.md](references/reporting.md) and write the report with objective metrics, review findings and unresolved blockers separately. Link research outputs in the conversation using workspace-relative Markdown paths so the existing file inspector/artifact UI can open them.

## Workspace and continuation

Use `research/<research-id>/` with `plan.md`, `evaluation.yaml`, optional evaluator and `baseline.json`, `state.json`, `evidence.md`, `experiments/<candidate-id>/` with hypothesis, code, parameters, logs and structured result, protocol revision snapshots and `report.md`. These files hold semantic checkpoints; Session/Runs/Artifacts/Provenance remain authoritative execution records. Do not create a new event log or scheduling state machine.

After each consequential result and before stopping, atomically save a checkpoint containing protocol version, current phase, remaining budget, completed experiment IDs and input/evaluator digests, saved result paths, evidence gaps, blockers, next actions and session/run/artifact references. Preserve protocol/evaluator revisions and the reasons for changes. Checkpoint after a tool result rather than marking an unfinished experiment complete.

On "continue"/"resume", read the plan, protocol, state, evidence and existing results first. Reuse completed experiments whose inputs and evaluator versions match; inspect existing run results before repeating an interrupted operation. Reassess affected results after protocol changes. Bind the new operation to the same `research_id` before execution; inspect its durable remaining allowance, never silently replenish it or substitute a new ID. Wall-clock expiry remains expired across continuation. An expired budget requires an explicitly agreed new research scope with preserved history. Do not promise browser-close/background autonomous recovery; the user can return to the conversation and continue using saved context.

Historical research archives in Knowledge are read-only source records. To continue one, inspect the linked archive and original artifacts, create a new skill workspace and protocol, carry over valid results with their original references, and explicitly state the old task is not being restarted by its former scheduler.
